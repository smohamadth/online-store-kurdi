# Project-wide audit — September 2026

Scope: the whole platform, not just the design tools (those are covered by
`STORE_BUILDER_BUGS.md` and `docs/DESIGN_WORKFLOW.md`).

Method: read every security boundary (payments, downloads, auth, money and
stock math), then re-verify each suspected problem against the code in this
checkout rather than against an older description of it. Findings are split
into **reproduced** (a test or a code path proves it), **hardened** (a
previously-reported hole that the current code already closes — recorded so it
is not "re-found" every audit) and **needs a live environment** (cannot be
settled in this sandbox).

## 1. Reproduced and fixed in this pass

### 1.1 A real zero tax was replaced by a phantom 10% — **P0 (money shown ≠ money charged)**

`apps/web/app/checkout/CheckoutView.tsx`

```ts
const taxAmount = taxInfo?.taxAmount || subtotal * 0.1;
```

`||` cannot tell "no calculation yet" from "the calculation returned 0". A
tax-free region, or a store with no tax rules at all, produces `taxAmount: 0` —
a **correct** answer — and the summary silently substituted a 10% estimate.

Impact: the customer reviews and agrees to a total the store never charges.
The server recomputes tax from its own rules (`order.routes.ts` deliberately
ignores the client's `taxAmount`), so the order is created with the honest
total and the checkout page has lied. On a 50 subtotal the page showed 55.

Fix: fall back only when there is no finite number at all.

```ts
const taxAmount =
  typeof taxInfo?.taxAmount === 'number' && Number.isFinite(taxInfo.taxAmount)
    ? taxInfo.taxAmount
    : subtotal * 0.1;
```

Covered by `app/checkout/CheckoutView.audit.test.tsx` — a zero calculation now
renders a 50.00 total, and a missing calculation still estimates 55.00.

### 1.2 Returning from a hosted gateway bounced the customer to /cart — **P0 (a paid order looks lost)**

Same file. The cart is cleared when the order is placed, so a customer coming
back from Zarinpal / IDPay / PayPal / ZainCash / FIB always has an empty cart.
The empty-cart guard fired on that render:

```ts
if (items.length === 0 && !orderPlaced && !returnState) router.push('/cart');
...
if (items.length === 0) return null;
```

`returnState` only covers the Stripe `?paid=true` / `?canceled=true` flags.
The gateway return is `?gateway=..&order=..`, and `gatewayReturn` is set
**asynchronously**, after the server-side verify resolves — far too late. The
customer was redirected to an empty cart and never saw the confirmation, while
the verify call (which is what settles the order in the storefront path) may
have been unmounted mid-flight.

Fix: derive the gateway return synchronously from the URL and exempt it from
both guards. Covered by the same test file, including the negative case (a
plain empty cart still redirects).

### 1.3 Rate limiting was one flat budget on a misidentified client — **P1 (self-inflicted outage)**

`apps/api/src/app.ts`, now `apps/api/src/config/rateLimits.ts`

Two faults that combined into a store-wide denial of service.

**One budget for everything.** A single `/api/` limiter allowed 100 requests
per 15 minutes. A storefront page view makes ~8 calls (settings, menus,
categories, products, banners...), so a genuine shopper was cut off after
roughly a dozen pages. The existing code knew about this and skipped GETs —
but only `isDevelopment`, so production kept the broken behaviour. Worse, the
shared bucket meant browsing traffic consumed the budget that protects
checkout and login.

**The client was misidentified.** `express-rate-limit` keys on `req.ip`, and
Express only derives that from `X-Forwarded-For` when `trust proxy` is set.
Nothing set it. Behind the reverse proxy that `docs/DEPLOYMENT.md` tells
operators to add, **every visitor shares one identity** — the proxy's. The
100-request budget became a budget for the entire internet, and the per-IP
login lockout in `utils/authThrottle.ts` (20 failures = 15-minute lock) would
have locked out every customer at once. The same `req.ip` feeds newsletter
consent records and analytics, so those were wrong too.

Fix: three budgets sized to what the traffic costs, and an explicit hop count.

| Budget | Default | Covers |
|---|---|---|
| read | 1000 | GET/HEAD/OPTIONS — ~125 page views per window |
| write | 100 (`RATE_LIMIT_MAX`, unchanged meaning) | checkout, cart, reviews |
| auth | 20 | login, register, forgot/reset password |

Each budget keys separately, so reads cannot starve checkout. `/auth/me` and
`/auth/refresh` stay on the read budget — putting them on 20-per-window would
log active shoppers out. CORS preflights to login are not charged as auth
attempts. The limiter is disabled under `NODE_ENV=test` so the integration
suite cannot throttle itself.

`TRUST_PROXY_HOPS` is a **count**, never a boolean: `trustProxyHops()` rejects
`'true'`, negatives and decimals, falling back to `0`. Trusting all hops would
let a client forge `X-Forwarded-For` for a fresh bucket per request and poison
every recorded consent IP — failing closed (over-strict for shared-NAT
visitors) is the safer default when nobody has configured it.

Covered by `tests/unit/config/rateLimits.test.ts` (12 tests). Documented in
`.env.example`, `SCALING.md` and `docs/DEPLOYMENT.md`.

### 1.4 The free-goods flag had no production guard — **P0 (inventory given away)**

`apps/api/src/config/environment.ts`, `modules/payments/payment.routes.ts`

`POST /api/payments/process` settles an order without talking to any gateway.
It is staff-only precisely because a customer who reaches it marks their *own*
order paid for free — and for a digital product the download token unlocks the
instant the order flips.

`PAYMENTS_ALLOW_MOCK=true` re-opens it to everyone. That is correct for a
local demo; the bug was that the route read the raw environment variable:

```ts
const mockAllowed = process.env.PAYMENTS_ALLOW_MOCK === 'true';
```

No production check, and not part of the validated env schema, so nothing
stopped the flag reaching a live store — one copied config file and the shop
gives away stock to anyone with an account.

This codebase already had the right pattern for exactly this hazard:
`exposeResetToken()` refuses in production, reads `process.env` live so the
refusal is testable, and checks for production **explicitly** rather than
trusting `isDevelopment` (`NODE_ENV` defaults to `'development'`, so gating on
it is fail-open — there is even a source-level ratchet in
`tests/unit/security/insecureEnvDefaults.test.ts` forbidding that shape).

Fix: `allowMockPayments()` mirrors it exactly. Plus two belt-and-braces
additions:

* **The production API now refuses to boot** when the flag is set, alongside
  the existing placeholder-credential check. Silently ignoring a config that
  reads "free checkout enabled" is a trap for the next operator; failing loudly
  gets it removed from the deployment.
* **A source ratchet** fails the build if `PAYMENTS_ALLOW_MOCK` is read
  anywhere outside `config/environment.ts`, so a future caller cannot
  re-introduce a bypass.

Covered by 5 tests in `insecureEnvDefaults.test.ts`. Verified by reverting the
guard: the production test fails, then passes again with it restored.

### 1.5 A failed SMTP connection silently dropped every email — **P0 (customers get nothing)**

`apps/api/src/services/email.service.ts`

The roadmap calls transactional email the single biggest launch blocker, on
the understanding that without SMTP the store falls back to *logging* every
message. It did not. `initializeEmail()` assigned the transport **before**
verifying it:

```ts
transporter = nodemailer.createTransport({ ... });
await transporter.verify();   // throws -> caught -> warning logged
```

When SMTP was unreachable — the default state of any store that has not set
it up yet — the broken transport stayed installed. Two consequences:

* `isEmailConfigured()` returned `true`, so the admin **"send test email"**
  button reported *"Test email sent successfully"* for mail that never left
  the building. The one tool a merchant has for checking email says the
  opposite of the truth.
* `sendEmail()` saw a truthy transporter and took the real-send branch, where
  `sendMail()` threw and was swallowed by the catch. The documented log-only
  fallback **never ran**, so order confirmations vanished leaving only a
  generic error line — no recipient, no subject, nothing to recover from.

Fix: build into a local, verify, and only then publish it; on failure clear
the transport and name the reason in the warning. A store that loses working
SMTP later (rotated credentials, mail host down) now degrades to log-only on
re-init instead of continuing to claim delivery.

Covered by 4 tests in `tests/unit/email-init.test.ts`. Verified by restoring
the original assignment order: 3 of the 4 fail, then pass again with the fix.

## 2. Already hardened (verified, no action)

These were real at some point and the current code closes them. Listed with
the mechanism so the next audit can confirm quickly instead of re-litigating.

| Concern | Where | Why it is closed |
|---|---|---|
| Free goods via the mock payment endpoint | `payments/payment.routes.ts` `POST /process` | Staff-only; the demo flag is now refused in production (§1.4). Also refuses `method: 'refund'` (which would otherwise mint a fake refund and shrink the refundable balance) |
| Duplicate `Payment` rows on webhook retry | `markOrderPaidByStripe`, `settleOrderPaid` | Payment row + order flip in one `$transaction`, deduped on the gateway's stable `transactionId`; an orphaned row repairs the order instead of duplicating |
| Unpaid digital downloads | `downloads/downloads.service.ts` | Tokens are minted at placement but `redeemToken` refuses any order whose `paymentStatus` is not in `PAID_STATUSES`, and logs the attempt as `unpaid` (402) |
| Download token guessing / limit bypass | `downloads.helpers.ts` | 256-bit base64url tokens; expiry, per-token and per-product limits are pure predicates with unit coverage; increment + audit row are transactional |
| Cancelled/declined gateway returns treated as paid | `zarinpal.ts`, `idpay.ts`, `zaincash.ts`, `paypal.ts` | Each verifier rejects the callback's own failure signal (`Status != OK`, IDPay status outside 10/100/200, ZainCash JWT signature via HS256, PayPal capture status) **before** trusting it, and the settle is server-to-server |
| Client-supplied prices/totals | `orders/order.routes.ts` | Subtotal from DB prices, tax/shipping from server rules, discount re-derived from the coupon; the client's `subtotal`/`taxAmount`/`totalAmount` are accepted and ignored |
| Wallet debit stranded by a failed placement | `orders/order.routes.ts` | Store-credit and gift-card debits are reversed **in the store's currency** and the order deleted if placement then fails |
| Zarinpal refunds using the wrong reference | `gateway.service.ts` | The create-time authority is preserved as `gatewayResponse.originalReference` and preferred for Zarinpal refunds |
| Stored XSS through builder/CMS content | `utils/sanitizeRichText.ts`, `scrubBuilderConfig.ts`, `safeUrl.ts` | HTML fields sanitised on write; link fields restricted to http(s)/mailto/tel/relative; media fields to http(s)/relative; applied to pages, blog, products, translations, Home sections and Studio layouts |
| Zip-slip via theme/plugin upload | `utils/zipPackage.ts` | Entry names with `..`, absolute paths, backslashes or drive letters are rejected; entry/total/count caps |
| Placeholder secrets reaching production | `config/environment.ts` | Production boot refuses known placeholder values and `your-`/`changeme`-style markers — length validation alone would accept the published 46-char example JWT secret |

## 4. Could not be settled in this sandbox

* **No real database.** The API integration suite runs against the repository's
  in-memory Prisma mock, so transaction semantics, unique constraints and
  concurrent-checkout races are asserted against the mock's behaviour, not
  Postgres's. The `$transaction` + dedupe logic in `settleOrderPaid` deserves a
  real concurrency test.
* **Prisma cannot generate here.** `prisma generate` reaches
  `binaries.prisma.sh` for the query engine and the sandbox has no outbound
  access to it, so `npm ci` must be run with `--ignore-scripts` and no E2E run
  is possible. (The Docker image already works around this by generating both
  clients at build time.)
* **No live payment providers.** Every gateway verifier was reviewed by reading
  it against the provider's documented callback contract; none was exercised
  against a sandbox merchant account.
