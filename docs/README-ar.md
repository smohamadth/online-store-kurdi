# المتجر الإلكتروني — منصة تجارة إلكترونية ذاتية الاستضافة

**منصة تجارة إلكترونية متكاملة تستضيفها على خادمك الخاص.**
صُممت للشركات الصغيرة والمتوسطة — ثبّتها على خادمك، وكن مالك بياناتك،
وامددها بحرية.

## ١. ما هو هذا المشروع

متجر متكامل في مستودع كود واحد (مستودع npm موحد):

- `apps/api` — واجهة REST مبنيّة على Express.js (TypeScript، ORM هو Prisma)
- `apps/web` — واجهة المتجر ولوحة الإدارة مبنيّتان على Next.js 14 (App Router، TypeScript)

تُثبَّت بأمر واحد على خادم العميل (`./scripts/install-store.sh`)،
تُشغَّل بأمر واحد في وضع التطوير (`npm run dev`)، وكل الإعدادات موثقة
في ملف واحد (`.env.example`).

**الكردية (السورانية) في صميم التصميم:** المتجر متاح بالإنجليزية
والكردية (السورانية) والعربية والتركية مع دعم كامل لكتابة RTL؛
اللوحة والتوثيق تتبعان اللغات نفسها.

## ٢. المزايا

### واجهة المتجر (عامة للعملاء)

- المنتجات: **مادية ورقمية** (تحميل برمز مخصص لكل طلب، حدود تحميل
  وتاريخ انتهاء)، المتغيرات (variants)، خيارات مُنوّعة (لون/مقاس...)،
  معرض صور، مخزون، طلب أثناء نفاد المخزون (backorder)، تنبيهات
  إعادة التخزين
- تصفح التصنيفات (متداخلة)، بحث، تصفية متعددة المحاور، مقارنة، «المشاهدة مؤخراً»
- سلة التسوق، قائمة الأمنيات، العناوين، إتمام شراء متعدد المراحل
- الدفع: **نقداً عند الاستلام وتحويل بنكي افتراضياً** (مسار دون بوابة،
  يُسوّيه الموظفون)؛ **البطاقة عبر Stripe اختيارية** لكل متجر
- الطلبات: تتبع، إيصال، سجل الطلبات، تحميل المنتجات الرقمية
- تقييمات مع صور، قسائم، بطاقات هدايا، عروض
- الصفحات والمدونة: محتوى بلوكات (عناوين، صور، أعمدة، تنبيهات،
  اقتباسات، معارض، أزرار) مع مسودة/نشر وروابط Slug تدعم يونيكود
- لغات المتجر: en / ku / ar / tr مع RTL؛ اختيار العملة ودعم
  تعدد العملات
- SEO: بيانات وصفية تُبنى على الخادم، بيانات منظمة JSON-LD (Product،
  Breadcrumb، WebSite، Article)، خريطة الموقع، robots.txt، Open Graph
- منشئ الصفحة الرئيسية (أقسام، بانرات، معرض)

### لوحة الإدارة (`/admin`)

لوحة المؤشرات، المنتجات، المتغيرات، التصنيفات، المخزون (الكميات،
المستودعات، التحويلات، الحجوزات، الجرد، قواعد إعادة التزويد، مخزون
القنوات)، الطلبات، العملاء، التقييمات، القسائم، بطاقات الهدايا،
الشحن (مناطق ووسائل)، الضرائب، الصفحات، المدونة، **المظهر (منتقي
القوالب + رموز التصميم)**، البانرات والمعرض، القوائم، **التحليلات**،
**الاستيراد/التصدير**، الإعدادات، المستخدمون (أدوار: admin،
مشرف/مدير، customer).

### المنصة

- **استيراد/تصدير جماعي** للمنتجات والتصنيفات (CSV أو JSON،
  معاينة، تنفيذ كل-أو-لا-شيء) — القسم ١٠
- **تحليلات واقتراحات** (اختيارية، أولوية لخصوصية المستخدم) — القسم ١١
- **نظام القوالب**: ٥ قوالب مدمجة، أداة تهيئة، معاينة حية،
  اختيار لكل متجر — القسم ٩
- تقييد معدل الطلبات، التحقق من المدخلات عبر Zod، مصادقة JWT
  (access + refresh)، تجزئة كلمات المرور عبر bcrypt، سيطرة وصول
  قائمة الأدوار (RBAC)
- الخدمات الاختيارية تتراجع بنعومة: بدون Redis → بدون تخزين مؤقت؛
  بدون MinIO → رفع على القرص المحلي؛ بدون SMTP → تُكتب الرسائل في السجل

## ٤. البدء السريع (تطوير)

**المتطلبات:** Node.js 18+، npm 9+. لا يُطلب خادم قاعدة بيانات
(يُنشأ ملف SQLite تلقائياً).

```bash
git clone <repository-url> && cd <repository>
npm install

# قاعدة البيانات: إنشاء ملف SQLite + المخطط، ثم تغذية الكتالوج التجريبي
npm run db:deploy        # apps/api/prisma/dev.db
npm run db:seed

# تشغيل الواجهة (:3001) + المتجر (:3000) معاً
npm run dev
```

> **ملاحظة لقاعدة بيانات جديدة:** `npm run db:deploy` يطبّق الترحيلات
> المسجلة. إذا تعذّرت قاعدة البيانات المحلية بعد تغيير مخطط، فالطريق الآمن هو
> `npm run db:reset` (حذف + إعادة إنشاء + تغذية).
> راجع [KNOWN_GAPS.md](../KNOWN_GAPS.md) القسم ٩.

### نقاط الوصول

| الخدمة | العنوان |
|---|---|
| المتجر | http://localhost:3000 |
| الواجهة | http://localhost:3001 (`/health` لفحص الحالة) |
| الإدارة | http://localhost:3000/admin |
| معاينة القوالب | http://localhost:3000/preview/default (و /minimal، /bold، /dawnlight، /pulse) |

### الحسابات المغذّاة

| الدور | البريد | كلمة المرور |
|---|---|---|
| مدير | `admin@store.com` | `admin123` |
| عميل | `customer@example.com` | `customer123` |

التغذية (seed) تنشئ أيضاً كتالوجاً تجريبياً (٥ تصنيفات من ضمنها
`General`، ٥ منتجات، تقييمات، قسائم، وسائل شحن، بانرات) و٥٠ صف
`UserEvent` اصطناعياً ليحصل داشبورد التحليلات على بيانات تجريبية —
صفوف عرض وليست بيانات زوار حقيقيين.

### التشغيل بدون Docker

كل شيء يعمل بدون Docker. ملفات compose في `docker/` مخصصة
للخدمات **الاختيارية** (Redis، MinIO، MailHog، PostgreSQL إن
غيّرت المزود):

```bash
npm run docker:up      # تشغيل الخدمات الاختيارية
npm run docker:down    # إيقافها
```

## ٥. الإعداد

كل الإعدادات في `apps/api/.env` (النموذج: `.env.example` في الجذر).
أهمها:

| المتغير | الغرض |
|---|---|
| `DATABASE_URL` | `file:./dev.db` (SQLite). يجب أن يطابق `provider` في `prisma/schema.prisma` — الاختلاف يسبّب خطأ Prisma P1012، وهو خطأ إعدادات وليس ثبّتاً معطوباً |
| `JWT_SECRET` | ٣٢+ حرفاً؛ برنامج التثبيت يولّد قيمة عشوائية |
| `REDIS_URL` | اختياري. غيابه → يُعطَّل التخزين المؤقت بصمت |
| `MINIO_*` | اختياري. غيابه → الرفع إلى القرص المحلي |
| `SMTP_*` / `EMAIL_FROM` | اختياري. غيابه → تُكتب الرسائل في السجل |
| `STRIPE_SECRET_KEY` / `STRIPE_WEBHOOK_SECRET` | اختياري. فارغاً → يخفى الدفع بالبطاقة، المسار دون بوابة فقط |
| `FRONTEND_URL` | العنوان الكامل للمتجر (روابط البريد، إعادة التوجيه) |
| `ANALYTICS_TRACKING_ENABLED` | **`false` (افتراضي).** `true` يُفعّل جمع أحداث السلوك — القسم ١١ وصفحة الخصوصية |
| `REVIEWS_AUTO_APPROVE` | `false` (افتراضي). `true` ينشر التقييمات دون مراجعة |
| `PAYMENTS_ALLOW_MOCK` | `false` (افتراضي). `true` يتيح لأي عميل تسوية طلبه بنفسه — **للعرض فقط** |
| `LOG_LEVEL` / `LOG_FILE` | الافتراضي `info`/`logs/app.log` |

### التبديل إلى PostgreSQL (اختياري)

1. اجعل في `apps/api/prisma/schema.prisma` القيمة `provider = "postgresql"`
2. وجّه `DATABASE_URL` إلى نسختك، مثلاً
   `postgresql://store_user:store_password@localhost:5432/store_db`
   (ملف compose للتطوير يوفر نسخة بهذه الاعتمادات مسبقاً)
3. `cd apps/api && npx prisma migrate dev` لبناء مخطط جديد

الكود مستقل عن مزود قاعدة البيانات: يتجنب مرشحات غير المتوافقة مع
SQLite (`mode: 'insensitive'`) ويعوّل على بحث في الذاكرة بدلاً منها؛
فلا يتغير شيء آخر. في الإنتاج، خذ نسخ احتياطية منتظمة بـ `pg_dump`.

## ٧. لمحة معمارية

**مسار الطلب (المتجر):** المتصفح → Next.js (مكونات الخادم تستلم
بيانات الصفحات المهمة لـ SEO من الواجهة؛ مكونات العميل للتفاعل) →
خط وسطّات Express (حد المعدل → تحليل JSON → المصادقة → التحقق Zod) →
مسار الوحدة → الخدمة → Prisma → SQLite/Postgres.

**وكيل الواجهة ← المتصفح:** `next.config.js` يعيد كتابة `/api/*` نحو
الواجهة و `/uploads/*` نحو MinIO؛ لذا يعمل النشر المشترك الأصل دون
إعداد CORS، حتى حين لا يصل المتصفح إلى مضيف الواجهة.

**المصادقة:** `POST /auth/login` يردّ برمز **access** + **refresh** قصير
العمر. يحتفظ المتجر بالرمز في `localStorage` (دون كوكيز تتبّع —
القسم ١١). الأدوار: `admin` (الكل)، `مشرف/مدير` (الكتالوج والطلبات
دون إدارة المستخدمين)، `customer`.

**نموذج البيانات (الجوهر):** المستخدمون، المنتجات (مع المتغيرات
وصور المنتج والخيارات المُنوّعة)، التصنيفات (شجرة ذاتية الإحالة)،
الطلبات + بنود الطلب، المدفوعات، التقييمات (وصورها)، السلة، قائمة
الأمنيات، العناوين، القسائم، بطاقات الهدايا، مناطق/وسائل الشحن،
الضرائب، المستودعات + نماذج المخزون، الصفحات/المدونة (بلوكات
المحتوى)، البانرات، القوائم، إعدادات المتجر، إعدادات القالب،
UserEvents (التحليلات).

**قواعد الصلابة المعمول بها:** الخدمات الاختيارية (Redis/MinIO/SMTP)
تتعطّل لكل ميزة على حدة دون إسقاط الطلب؛ لا تُسقط التحليلات الطلب
أبداً؛ عمليات الكتابة الإدارية تُتحقق قبل وصولها إلى القاعدة.

## ٨. دليل المتجر (لتشغيل الأعمال)

- **إضافة منتج**: الإدارة → المنتجات → *+ إضافة منتج*. املأ الاسم، SKU،
  السعر، التصنيف، الصور؛ أضف متغيرات أو خيارات عند الحاجة؛ المنتج
  الرقمي يأخذ رابط تحميل + حدود. الحالة `active` تنشره.
- **البيع دون بوابة بطاقات**: يقترح إتمام الشراء نقداً وتحويلاً بنكياً.
  تصل الطلبات بحالة `paymentStatus: pending`؛ يسوّيها الموظفون من
  الإدارة → الطلبات. (لا تُفعّل `PAYMENTS_ALLOW_MOCK` أبداً في متجر
  عام.)
- **تفعيل Stripe**: ضع المفتاحين في `.env`، وأضف webhook باسم
  `checkout.session.completed` في لوحة Stripe، وأعد التشغيل. يظهر خيار
  البطاقة تلقائياً.
- **القسائم وبطاقات الهدايا**: الإدارة → القسائم / بطاقات الهدايا.
  كلاهما يعمل عند إتمام الشراء؛ بطاقة الهدية تولّد رموز استرداد.
- **المحتوى**: الإدارة → الصفحات / المدونة — محرر بلوكات (إضافة
  عنوان، صورة، أعمدة، تنبيه، اقتباس، معرض، زر)، مسودة → نشر. الروابط
  آمنة ليونيكود (العناوين الكردية/العربية تعمل).
- **الصفحة الرئيسية**: الإدارة → أقسام اللوحة + البانرات والمعرض.

## ٩. القوالب

**القالب** مجلد تحت `apps/web/themes/<key>/`:

- `theme.json` — يُتحقق منه في وقت **البناء** بمخطط Zod صارم:
  الهوية (key، الاسم، المؤلف، semver)، `features` (`rtl`، `darkMode`،
  `paid`)، `tokens` (الألوان، الخطوط، انحناء الحواف، عرض الحاوية،
  ظل البطاقة، عدد المنتجات في الصف، مفاتيح الأقسام مثل `showTrustBar`)،
  وخريطة اختيارية `sections`
- `sections/*.tsx` — استبدال مكوّنات أقسام الصفحة الرئيسية
  (`hero`، `featured`، `categories`). الاستبدال يحل محل قسم المنصة
  بالكامل (لا يوجد وضع «تغليف» بعد).

**القوالب المدمجة (٥):** `default`، `minimal` (مدفوعة، نصية البنية،
خط serif)، `bold`، `dawnlight`، `pulse`.

**Theme Studio** — مُنشئ القوالب البصري وتخطيط كل صفحة. التوثيق الكامل: [`docs/THEME_STUDIO.md`](THEME_STUDIO.md).

**مسار المطور لقالب جديد:**

```bash
node scripts/scaffold-theme.mjs solar --name "Solar"
```

أداة التهيئة تضبط كل نقاط التسجيل (theme.json + ثلاث هياكل أقسام
متوافقة مع العقد وآمنة RTL، سجل القوالب، خريطة المكونات، مصفوفة
اختبار RTL، تثبيت اختبار منتقي القوالب). ثم عدّل الرموز والأقسام؛
ملف `theme.json` المعطوب يفشل **البناء** برسالة مسار واضحة؛ نسيان
تسجيل RTL يفشل مجموعة الاختبارات. عاين في `/preview/solar`؛ فعّل لكل
متجر من **الإدارة → المظهر**. تجاوزات رموز كل متجر تُطبَّق فوق القالب
المفعّل.

**الحدود (بصدق):** القوالب تُنسَّخ مع المنصة (مراجعة كود، وليس
رفعاً حياً)؛ `paid: true` مجرد بيانات وصفية (لا تحقق ترخيص ولا سوق
بعد)؛ `darkMode` شارة قدرة فقط.

## ١٠. الاستيراد/التصدير الجماعي

لمدراء admin + المشرفين فقط. الواجهة في `/admin/import-export`؛
الواجهة البرمجية في `/api/import-export`.

- **تصدير** — `GET /export/:entity?format=csv|json&sample=1` ل
  `products` (مع المتغيرات والصور وحقول SEO) و `categories`
  (مع روابط الأب). `sample=1` يعيد صف نموذج واحد.
- **معاينة** — `POST /preview {entity, format, text}`: تحليل +
  تحقق، وتصنيف كل صف إلى **جديد / تحديث / خطأ**، دون كتابة أي شيء.
- **تنفيذ** — `POST /commit`: يعيد التحقق من الملف الفعلي وينفذه
  **كل-أو-لا-شيء** في معاملة واحدة. خطأ في أي صف → لا يُنفَّذ شيء.

القواعد: تُطابَق المنتجات بـ **SKU** (جديد → إنشاء، موجود →
تحديث، تُتجاهل الخلايا الفارغة)؛ تُطابَق التصنيفات بـ **slug ثم
الاسم** (دون تمييز الأحجام)؛ عمودا `variants`/`images` إن وُجدا
يستبدلان السابق كلياً. المنتج بلا عمود `category` يوضع في تصنيف
التغذية `General`. الحد: ١٬٠٠٠٬٠٠٠ حرف / ٢٬٠٠٠ صف لكل ملف.

مُتحقق منه عبر ٢٩ اختباراً تكاملياً و١٤ اختباراً وحداتياً لمحلل CSV
و١٢ اختباراً لمكوّنات صفحة الإدارة وسكربت CI الحي
`scripts/verify-import-export.py`.

## ١١. التحليلات والاقتراحات والخصوصية

**معطَّل افتراضياً.** لا يعمل مسار الأحداث إلا عند تشغيل الواجهة
بـ `ANALYTICS_TRACKING_ENABLED=true`؛ بدونه تعيد مسارات التتبع
404 و**لا يُجمع شيء** (تُردّ طلبات أحداث المتجر بصمت).

عند التفعيل:

- **الأحداث**: `view`، `add_to_cart`، `wishlist` من المتجر
  (معرّف الجلسة من `sessionStorage` — لا كوكيز أبداً؛ يُرفق رمز
  bearer فقط عند تسجيل دخول المستخدم، فيربط الأحداث بالحساب)؛
  `search` و `purchase` تُسجَّل على الخادم (مسار البحث، إنشاء
  الطلب). يخزن كل حدث نوع الحدث، المنتج/التصنيف، نص البحث،
  الطابع الزمني، user agent و IP العميل.
- **المستهلكون**: **الأكثر رواجاً** في الصفحة الرئيسية (مبني على
  الأحداث)، **نشاط المتجر** في الإدارة (عدّادات اليوم، أكثر
  عمليات البحث خلال ٣٠ يوماً، رواج ٧ أيام)، **معدلات التحويل**
  لكل منتج (عرض → سلة → شراء)، سلوك المستخدم، و**محرك الاقتراح**
  (يتعلم also-bought من المشتريات المشتركة الحقيقية؛ اقتراحات
  مبنية على السجل من المشاهدات).
- **ما لا نفعله أبداً**: لا تحليلات خارجية افتراضياً (Google
  Analytics فقط إن ضبط صاحب المتجر معرّف property)، لا بيع أو
  مشاركة للبيانات، لا كوكيز تتبّع — حالة الدخول والتفضيلات في
  `localStorage` المتصفح.
- **سجل الخادم** يحوي دائماً IP العميل (تسجيل ويب قياسي)؛ نص
  البحث يظهر في السجل فقط عند `LOG_LEVEL=debug`.

صفحة `/privacy` توثّق كل ذلك وتحمل ملاحظة صيانة: إن تغيّر السلوك،
تتغير الصفحة في نفس الالتزام.

## ١٢. لمحة الواجهة البرمجية

REST، JSON، محمية بـ JWT حيث يلزم. الأصل: `/api`.

- **المصادقة**: تسجيل، دخول، تحديث، خروج، من-أنا، نسيان/إعادة تعيين كلمة المرور
- **المنتجات**: قائمة (تصفية متعددة المحاور + بحث)، مميزة، `search`،
  بالـ id/slug، ذات صلة، CRUD (مدير)، متغيرات وخيارات
- **الطلبات**: قائمة، إنشاء، تحديث الحالة (مدير)، إلغاء، إيصال،
  تتبع، رمز تحميل لكل بند
- **المدفوعات**: process (تسوية الموظفين)، Stripe Checkout + webhook
- **المستخدمون / العملاء**: CRUD (مدير)، طلبات وقائمة أمنيات كل مستخدم
- **عمليات الكتالوج**: التصنيفات (شجرة)، المخزون والمستودعات،
  القسائم، بطاقات الهدايا، الشحن، الضرائب
- **المحتوى**: الصفحات، المدونة، البانرات، القوائم، أقسام
  الصفحة الرئيسية، الإعدادات، القالب
- **عمليات المتجر**: `import-export` (القسم ١٠)، `analytics`
  (القسم ١١)، `recommendations` (رواج، الوافد الجديد، also-bought،
  bought-together، سجل، مخصص)، `downloads`، `currency`، `storage` (رفع)
- **الحالة**: `GET /health`

المصدر المرجعي: `apps/api/src/modules/*/…routes.ts` (كل مسار إما
لديه اختبار وحداتي/تكاملي أو تغطيه سكربت حي `verify-*.py`).

## ١٣. قاعدة البيانات

**افتراضياً: SQLite** (`apps/api/prisma/dev.db`) — صفر تثبيت؛
يُنشأ الملف بـ `npm run db:deploy`. يدعم PostgreSQL بالكامل (القسم ٥).

```bash
npm run db:deploy     # تطبيق الترحيلات (migrate deploy)
npm run db:migrate    # تطوير: إنشاء/تطبيق ترحيل
npm run db:seed       # كتالوج تجريبي + حسابات
npm run db:reset      # حذف، إعادة إنشاء، تغذية
npm run db:studio     # واجهة Prisma Studio الرسومية
npm run db:generate   # إعادة توليد العميل بعد تعديل المخطط
```

عيب معروف: مجموعة الترحيلات المسجلة تتأخر عن بعض تغييرات
المخطط (الحالة الصادقة في [KNOWN_GAPS.md](../KNOWN_GAPS.md) القسم ٩) —
لقاعدة محلية جديدة، `db:reset`/`prisma db push` + التغذية هو
الطريق الآمن.

## ١٤. الاختبار و CI

| المجموعة | الأمر | ما يلزم |
|---|---|---|
| وحداتي API | `npm run test:api:unit` | لا شيء (Vitest) |
| تكاملي API | `npm run test:api:integration` | لا شيء — **mock-Prisma** في الذاكرة، دون قاعدة |
| مكتبة الويب | `npm run test:web:lib` | لا شيء (Vitest + happy-dom) |
| مكوّنات الويب | `npm run test:web:components` | لا شيء (RTL + happy-dom) |
| regression حي (API) | `bash scripts/regression.sh` | API يعمل + بيانات تغذية |
| regression حي (متصفح) | `ui-checks` في CI | API + متجر مبني، Playwright |
| مُحقِّقات الميزات | `python3 scripts/verify-*.py` | API يعمل (+ المتجر لمهام المتصفح) |

يعمل CI (`.github/workflows/ci.yml`) وظيفتين متوازيتين مع كل دفع
إلى `main`: **api-checks** — فحص قالب البيئة، الترحيلات، تغذية،
تشغيل الواجهة، `regression.sh`، `audit-silent-writes.py`،
`verify-commerce.py` و `verify-import-export.py` — و **ui-checks** —
`next build`، تشغيل الواجهة + المتجر، ثم مجموعات Playwright: جولة
الصفحات، منشئ الرئيسية، البانرات، المعرض، أكواد الحالة 404، حراسة
أدوار المستخدم، أرقام اللوحة، الصفحات + العمود الجانبي، المدونة،
هندسة العمود الجانبي، روابط يونيكود.

## ١٥. النشر

**تثبيت العميل (موصى به):** على مضيف Docker —

```bash
git clone <repo> /opt/store && cd /opt/store
./scripts/install-store.sh     # compose (ملف الإنتاج) + تغذية، أمر واحد
```

البرنامج المثبِّت يولّد `JWT_SECRET` عشوائياً جديداً، ويبني
`docker-compose.prod.yml` (api + web + postgres + redis + minio +
mailhog)، ويُوحِّد قاعدة البيانات عند أول إقلاع، ويغذّي عبر
حاوية الواجهة. التفاصيل الكاملة:
**[DEPLOYMENT.md](DEPLOYMENT.md)** (الوضع A Docker،
الوضع B بلا Docker).

**يدوياً:** `npm run build && npm run start` (أو Dockerfiles
`Dockerfile.api` / `Dockerfile.web`). ضع المتجر خلف TLS؛ وضّب
`FRONTEND_URL` و `CORS_ORIGIN` و SMTP و (اختيارياً) Stripe في
`apps/api/.env` قبل الإطلاق.

## ١٦. استكشاف الأخطاء (مضغوط)

| العرض | السبب والإصلاح |
|---|---|
| `the URL must start with the protocol 'file:'` (P1012) | `DATABASE_URL` لا يطابق `provider` في المخطط (يتطلب sqlite بادئة `file:`). طابقهما — خطأ إعدادات وليس ثبّتاً معطوباً |
| المتجر يعمل لكن «الصفحة غير موجودة» لصفحة منشورة | فقط **404 قاطع من الواجهة** يعرض not-found؛ أعطال الواجهة تعرض صفحة خطأ مؤقتة صريحة (فشل مفتوح، عمداً) |
| 500 لصفحة المنتج وقت الطلب | افحص `og:type` — Next.js ترفض `"product"`؛ الكود يستخدم القيم المسموحة |
| صفحة الإدارة تُعرض بلا بيانات | الواجهة لا تعمل، أو `NEXT_PUBLIC_API_URL` يشير إلى مضيف لا يصله المتصفح — تطبيق الويب يوّكّل `/api` مشاع الأصل (القسم ٧) |
| خيار البطاقة مفقود عند إتمام الشراء | مفاتيح Stripe غير مضبوطة (أو webhook مفقود) — متوقع: يعود المتجر إلى المسار دون بوابة |
| الرسائل «لم تُرسَل» | SMTP غير مضبوط → تُكتب في السجل (افحص `LOG_FILE`). استخدم MailHog محلياً |
| بيانات قديمة بعد تغيير المخطط | محلياً: `npm run db:reset`؛ لمجموعة الترحيلات: `scripts/sync-migrations.sh` |

تاريخ الإصلاحات الكامل في git؛ الثغرات الحالية في
[KNOWN_GAPS.md](../KNOWN_GAPS.md).
